# 缺陷与发布候选政策

负责人：产品负责人；源码核对：2026-09-25。每个缺陷用稳定 `BUG-YYYYMMDD-NNN`，关联[能力矩阵](feature-test-matrix.md)的 Test ID 和[轮次记录](runs/_template.md)。这是一人能维护的短记录，不建额外看板。

## 严重度与发布影响

| 级别 | 定义 | Ohana 例子 | 决定 |
| --- | --- | --- | --- |
| P0 | 数据丢失、隐私泄露、不可恢复的核心错误或大范围崩溃 | 恢复失败覆盖原 SwiftData；锁屏 Widget 显示健康笔记；照护写入后账本可重放不一致 | 立即 NO-GO，停止相关测试并保护现场 |
| P1 | 核心承诺失效，且无可接受绕路 | 喂食按钮显示成功但重启后事实消失；提醒 action 重复发奖；Personal 已购无法恢复；签名 App Group 不可读 | NO-GO，聚焦修复并换 RC |
| P2 | 有安全绕路的局部错误 | 非关键筛选错位、某语言次要文案截断、一个非核心图表延迟 | 可讨论 `CONDITIONAL GO`，写明范围、绕路、负责人和后续期限 |
| P3 | 轻微修饰或未来范围 | 不影响操作的图标间距、Family 未来能力建议 | 记录，不自动阻断 1.0 |

**状态**：`NEW → REPRODUCED → ROOT CAUSE FOUND → FIXED → RETESTING → CLOSED`；若证据表明不是产品问题，改 `TEST DEFECT` 或 `ENVIRONMENT BLOCKED`，保留原始失败。`CLOSED` 需确切 RC、修复 commit、回归测试、首次失败解释、受影响路径复测证据。未复现不等于不存在，记录环境和复现尝试。

## 失败后的固定循环

```text
失败 → 记录原始证据 → 在确切 RC 复现 → 分 P0–P3
     → 找根因 → 增加有意义的回归证明 → 聚焦修复
     → 跑目标 Unit/Integration → 跑受影响 UI shard（若适用）
     → 跑必需仓库门 → 冻结新 RC → 重跑发行 smoke 和受影响硬门
```

手工测试时先完成该组并记录现场，暂不在同一会话改代码。原因是修复后已变为新二进制；旧截图不能同时证明新 RC。一个失败若只在重试通过，仍是“首次 FAIL + 后续 PASS”；先调查竞态、环境、顺序依赖或测试自身错误。只删/跳过断言让 CI 变绿不关闭缺陷。

变更源码、资源、编译设置、entitlement、签名或 build number 后，影响二进制身份，旧 RC 不能再作为可提交产物；冻结新 RC。未受影响的旧证据可保留作**历史对比**，不能自动填新轮次 `PASS`。新 RC 必须重跑：静态/Unit 完整门、完整 UI 分片、发行 smoke、受影响功能与迁移、最终 Archive/Privacy Report、同一 build 的 TestFlight/真机/StoreKit 硬门。若只是 App Store 文案更正，源码测试可引用同一未变 build 的记录，但仍要重核文案、截图、账号和提交状态。具体最小重测范围由[发布质量门](../release-quality-gates.md)裁决。

产品缺陷与测试缺陷分开：若真实 UI 不符合产品合同，是产品；若 AX 查询竞态但界面状态正确，优先是测试；若模拟器/runner/账号不可用且产品尚未到达，则是环境阻塞。三者都要记录原始步骤与证据，不能凭猜测分类。避免“把整个模块重构一遍”的 AI 修复：先明确一个不变量、一个 owner service、最小代码范围和一条可失败的回归证明；无关问题另建 ID。
