# 入门与进度：先知道现在在哪，再决定下一步

适用对象：Ohana 产品负责人，以及接手发布工作的 Codex。进度快照基于 2026-09-25 的源码 HEAD 116ea499f1d005c55d49332db63ded7bc428dafc（分支 agent/fix-water-refill-care-fact）；每次开始一轮新发布工作时，先重新核实 Git 与实际产物，再更新本页。

## 如果你是第一次做软件发布

先记住一句话：**“代码写好了”不等于“已经证明这个版本可以安全交给用户”。** 发布要确认用户能安装和升级、重要数据不会丢、付费和隐私声明正确，而且送交 Apple 审核的二进制确实是测试过的那个版本。

### 什么是“发布文档包”？

它是一组给人使用的说明书、检查清单和记录表。它们不是 Ohana App 的一部分，也不会自动运行测试或替你提交 App Store。它们解决的是“下一步做什么、用什么设备、怎样算通过、证据放哪里、出错后怎么办”这些容易靠记忆遗漏的问题。

可以把它想成一次长途旅行的准备资料：

- **说明书**告诉你流程和安全规则，例如先在哪种设备测试，什么时候需要第二台 iPhone。
- **测试清单**告诉你每项功能应该看到什么，例如完成喂食后，历史、库存和奖励是否都正确。
- **轮次记录**记下这一次具体用了哪份代码、哪个 App build、哪台设备和最终结果。下次发布会有新的记录，不能拿上次旅程的检查表当成本次已经走过的证明。

如果没有这些资料，过几周后很难记清某个“通过”到底对应哪份代码、哪个 build 或哪台设备。一个按钮能点不代表照护事实真的保存；新安装成功也不代表旧用户升级后数据安全；Simulator 上没问题也不代表真机锁屏通知可靠。文档包让你和 Codex 可以沿着同一份清单工作，还能回头检查证据。

### 什么是“发布”？

“发布”是把一个确定版本交给真实用户使用的整段过程，不只是按 Xcode 的 Archive 按钮，也不只是把 App 上传到 App Store Connect。大致包括：确定这版要提供什么、验证功能和旧数据、生成可分发的签名包、核对隐私和商店资料、让测试者试用、提交 Apple 审核、审核通过后上架，再观察用户反馈。

以 Ohana 为例，喂食记录要能保存并在重启后读回；付费状态不能让免费照护数据消失；Widget 不能泄露锁定成员的健康信息；App Store 的隐私答案和实际数据处理也必须一致。每一项需要不同的检查，所以发布要分步骤完成。

### 什么是 RC？为什么要“冻结”？

RC 是 Release Candidate 的缩写，中文常说“发布候选版本”。它的意思是：**“我们认为这份确定的代码可能可以上架，现在要对它做最终检查。”** RC 不是另一个 App，也不表示它已经合格或可以提交。

一个 RC 至少要能回答：

- 用的是哪一份代码？用 Git commit 的 SHA（类似代码版本的唯一指纹）识别。
- 用户安装的是哪个版本和 build number？例如源码配置目前显示 1.0 (1)。
- 实际测试的是哪一个安装包、设备和系统版本？
- 测试结果和签名 Archive 是否都属于同一个版本？

**冻结代码**是指先选定一个 commit，在这轮验证期间不再悄悄混入别的代码改动。可以把它想成考试时先印好试卷版本：如果测试中途换了题目，就要标明新版本，并重新确认受影响的题目。否则你无法证明最后要交给 Apple 的包就是之前测过的包。

RC 后若源码、图片资源、签名能力或 build number 改变，通常就要建立新的 RC 身份，并按影响重跑检查。先前的结果仍可保留作历史对比，但不能自动算作新 RC 的通过证据。

### 门禁、Test ID 和“证据”是什么意思？

- **门禁**：发布前的一项检查和明确的通过条件，例如“Unit 测试完成”或“第二台设备恢复后旧数据仍完整”。只有满足条件并留下证据，才关闭这一项。
- **Test ID**：一个稳定编号，例如 OHANA-FEED-001。它像清单上的条目号码，让测试步骤、缺陷和轮次结果说的是同一件事。
- **证据**：别人可以复核的记录，例如命令结果、Xcode 测试报告、CI 运行链接，或你在指定真机上看到的脱敏观察。只看源码或测试代码只能说明“项目里写了这种检查”，不能说明“这次真的跑过并通过”。
- **PASS**：指定代码和 build 在指定环境完成规定步骤，结果符合预期，并且证据已记下来。
- **NOT RUN**：还没有执行。它不代表失败，也不代表通过。
- **BLOCKED**：想做这项检查，但缺少必要条件，例如没有 Distribution profile、没有第二台可擦除测试 iPhone 或没有 Sandbox 商品。
- **NO-GO**：还有重要检查没完成或存在未解释的问题，当前不能提交。它不表示 App 的所有功能都坏了。

发布中常见的证据边界：Unit 测试可以验证一段规则，但不能证明用户找得到按钮；Simulator 可以演练 UI，但不能证明真实通知能在锁屏送达；测试通过一次也不能抹掉第一次失败且原因不明的记录。

### 从改动到上架，会经历什么？

1. **确定范围**：说清这次包含什么、不包含什么。Ohana 1.0 是本机 Solo Free / Personal；Family 守护能力仍在 1.0 发布范围之外。
2. **验证改动**：先跑与改动相关的窄检查。例如修照护命令，就验证相应事实与账本；改界面入口，再确认实际页面路径。
3. **选定候选**：确定 commit、版本号和 build number，建立 RC 身份。
4. **验证候选**：跑发布静态门、Unit/Integration 和 UI 回归；根据功能风险继续做迁移、真机、第二设备或购买测试。
5. **制作最终包**：用 Apple Distribution 签名生成 Archive，检查 App 和 Widget 的签名能力，并从最终包生成隐私报告。
6. **核对商店资料**：在 App Store Connect 检查商品、价格、截图、年龄评级、出口合规、隐私答案和审核备注。
7. **决定并提交**：负责人确认同一 build 的关键证据齐全，作 GO 决定，再由账号持有人提交 Apple 审核。
8. **上架后观察**：查看崩溃、用户反馈和购买恢复问题；若改代码修复，就对新 build 建立新的验证记录。

### 这些百分比是怎么算的？

- **11/11 = 100% 文档**：预定的 10 份发布操作/记录文件都已建立，再加上本入门页，共 11 份。它回答的是“说明资料是否写齐”，不回答 App 是否能上架。
- **46/46 = 100% 追踪条目**：能力矩阵 A 表中的 46 个 Test ID，在 B 表中各有一条覆盖和下一步记录。它回答的是“有没有为这些能力安排验证”，不回答功能开发是否完成，也不回答测试是否通过。
- **0/12 = 0% 当前门禁证据已关闭**：当前候选页有 12 个发布检查项，目前没有一项有证据可标成关闭/通过。它回答的是“当前代码版本有多少发布检查已留证据”。其中一些还没运行，一些需要你掌握的 Apple 账号或实体设备。
- **整个 App 的功能完成率暂时不报百分比**：需要先有所有功能及其完成定义作为可靠分母。仅仅数源码文件、按钮或测试用例，不能诚实地换算成“产品完成百分比”。

所以当前阶段可以概括为：**发布流程和检查资料已准备好；当前代码还没有经过一整轮可追溯的 RC 验证；外部账号和真机发布证据也尚未齐备。**

### 常见词快速解释

| 词 | 小白版解释 | Ohana 中的例子 |
| --- | --- | --- |
| commit / SHA | 一次保存到 Git 的代码快照；SHA 是这份快照的唯一指纹 | 116ea499 是当前文档所依据的代码提交 |
| App version / build number | 面向用户的版本号 / Apple 用来区分每个安装包的递增编号 | 当前源码配置是 1.0 (1)；这不说明 Apple 后台已经收到它 |
| Simulator | 在 Mac 上模拟出来的 iPhone | 可用来练习首启和多数 UI 自动化，不能证明真机通知或后台定位 |
| Unit / Integration / UI test | 检查一条规则 / 检查多个模块一起工作 / 自动操作真实界面 | Unit 可检查椰子账本规则；Integration 可检查任务完成后是否写入 watering 事实；UI test 检查人能否从页面完成操作 |
| Archive | Xcode 生成、准备签名和分发的构建归档 | Archive 还不是已上传的 App Store build，也不是审核通过 |
| Distribution signing | Apple 用发布证书确认是谁发布 App、允许哪些系统能力 | App 和 Widget 的 App Group 都要与签名材料一致 |
| App Store Connect（ASC） | Apple 管理 App、商品、TestFlight 和审核提交的网站 | 账号里的商品、协议和 build 状态必须实际登录核对 |
| TestFlight | Apple 提供的 beta 测试分发服务 | 可让测试者试同一个上传 build；它仍不等于 App 已公开上架 |
| StoreKit Sandbox | Apple 的购买测试环境 | 可测订阅、取消和恢复，不使用真实购买账号来测试 |
| GO / NO-GO | 有证据支持可以提交 / 目前证据不足或有风险，先不要提交 | 当前是 NO-GO，因为当前候选缺同一版本的测试与发行证据 |

## 最省力的使用顺序

1. 打开本页与[控制中心](README.md)，确认 HEAD、RC 身份、NO-GO/GO 决定和未关闭门禁。
2. 打开[测试策略](test-strategy.md)，确定动作在哪个安全环境运行，以及需要何种证据。
3. 在[能力矩阵](feature-test-matrix.md)找 Test ID、入口和结果合同；若是人工操作，先读对应[会话](manual-device-test-runbook.md)。
4. 在[轮次模板](runs/_template.md)的本轮记录中填 SHA/build/环境，并保留命令输出、xcresult、CI URL 或经过脱敏的人类观察。
5. 失败时先记录，不在现场边测边改；按[缺陷政策](defect-and-rc-policy.md)复现、分类、修复和换 RC。
6. 所有对应层级都有同一 RC 的证据后，按[上架手册](app-store-release-runbook.md)过提交门。App Store Connect 的最终 GO 由负责人签收。

## 负责人和 Codex 的分工

- Codex 可以检查源码、测试、脚本和 CI 配置；在仓库规则允许时运行本机静态门或测试；整理收据、做 Test ID 追踪，并解释失败。
- 负责人亲自在实体 iPhone 上确认通知、定位、HealthKit、相机、权限、锁屏、后台、能耗和 VoiceOver 等硬件/系统行为；真实观察由负责人报告。
- 第二设备恢复、加密系统备份排除只能在可擦除测试机与合成数据上做。
- App Store Connect、Developer Portal、Sandbox Apple Account、TestFlight、签名证书/profile 和最终提交由负责人控制；不要向 Codex 提供密码、receipt、未脱敏健康值、精确位置、原始数据库、私人照片或账号标识。
- 受保护的 iPhone 17 Dogfood 只允许遵照[仓库规则](../../AGENTS.md)和[Dogfood 手册](../dogfood-testing.md)执行的正常、非破坏性 UI。不要在上面重置、卸载、恢复、seed、跑 XCTest 或直接改 store/defaults。

## 读进度时记住

PASS 只表示指定 SHA/build、环境和步骤有真实收据；源码检查是 SOURCE VERIFIED，不是运行通过。Unit 不证明 UI，Simulator 不证明实体设备后台行为，TestFlight 也不等于 App Store 已发布。若本页与轮次文件数字不同，以[当前候选](runs/current-candidate.md)为执行状态唯一来源；若与现有仓库治理文档冲突，以 README 链接的权威文档为准，并将冲突记录下来，不要暗中改写旧记录。
