# Ohana AI 协作模块测试与修复手册（v2 · 多会话架构）

目标：按依赖顺序逐模块"分析 → 修复 → 补测试 → 门禁 → 人工验收 → 提交"，全部走完后进入上架准备。

v2 核心变化：
1. **多会话架构**——每个模块在独立 AI 会话中处理（避免 context 膨胀），一个总览会话负责调度与对账；所有进度状态只存在于文件，不依赖任何会话的记忆。
2. **模块退出自动门禁**——每个模块完成后，运行 `scripts/module-exit-gate.sh`，自动跑全套审计 + **整个 app 的完整单元测试**，门禁不绿不许提交。

诚实声明：没有任何流程能"保证"Apple 审核通过。本手册保证的是可控部分——代码质量、测试覆盖、合规审计、发布材料齐备——把审核风险压到最低。

## 一、会话架构（总览会话 + 模块会话）

| `docs/specs/<模块>-logic.md` | **模块业务规则书**：从代码反推、经你确认的业务不变量（见循环第 1b 步），复审与未来开发的基准 |

会话记忆不可信。换会话、断会话、并行会话，一切以上述文件为准。

### 模块会话（Worker）

一个会话只负责**一个模块**的完整六步循环。开工 boot prompt（直接复制）：

> 读 `AGENTS.md`、`docs/ai-module-test-playbook.md`、`docs/testing-progress.md`。
> 本会话只负责 **<模块名>**（Phase <X>）。范围限定在 `Ohana/Features/<模块名>`（或对应地基层目录），不许越界修其他模块。
> 先把 `docs/testing-progress.md` 中该模块状态改为 🟡 并填开工日期，然后从六步循环第 1 步开始：只分析，不修改。

**Phase 7 附加 boot prompt（标准模块 boot prompt 后追加）：**

> 1b 分析时额外预检五类已知模式（来自 Economy/旧删除模型复审）：① 本模块的奖励发放是否全部走预算/冷却管线，有无绕行路径；② 奖励归属是否按 executor、有无写 system 钱包；③ 显式 executor 为离世成员时是否全链路 no-op，invalid/missing/physically-deleted executor 是否仍保留 active 照护对象事实且奖励归属明确兜底；④ 派生状态生命周期是否完整（物理删除前 tombstone、级联、取消/重排边界）；⑤ 关键边界是在服务层硬门还是只有 UI 软门。命中任何一类直接列 P1。

收工协议（缺一项视为未完成）：
1. `scripts/module-exit-gate.sh` 通过（贴输出摘要）。
2. 按 Conventional Commit 提交，scope 用模块名。
3. 更新 `docs/testing-progress.md`：状态 🟢、门禁 commit 哈希、余留项指针、给下一个会话的交接备注。
4. 未修项写入 `docs/task-follow-ups.md`。
5. **每个完成的工作项或 coherent fix batch 收工即推送到 origin 并确认远端结果**。理由：SwiftLint 严格模式、SwiftFormat、全仓审计**只在 CI 跑**，本地默认门禁没有；没推到 CI 的工作 = lint/format/审计门尚未真正运行。硬边界：**`main` 领先 `origin` 不得超过一个已完成工作项或一个工作日**——超过就意味着这些 CI-only 门禁在睡觉，且日后一旦变红要跨多个 commit 二分（对账日志已两次记下这个违规：领先 9 个、14 个 commit）。一个工作项内的多个本地 commit、规则书回填、总账更新、纯文档收口、同一根因/同一审计规则/同一架构边界的一组修复，合并到该 work-item/batch 的收工 push 一起推；但**不再把多个工作项攒成一批**，也**不要把一个 coherent repair 拆成多个 push 只为采样 CI**。推送前先跑该 batch 的本地廉价门禁；推送后查看最新 run 一次并记录 URL/结论，不反复 poll。若 CI 因**已登记的外部 blocker** 红，记录对应 TFU 和通过的 job，不再反复触发同一红点（直到该 blocker 进修复轮）。

**验收债规则（人工验收的批量后置）**：需要真机/真实 iCloud/真实通知/真实数据的验收项，允许登记进 `docs/planning/gap-acceptance-track-list.md` 后先行提交，总账状态标 **🟢\***（带验收债）。约束：① 纯模拟器可完成的关键路径验收**不得**后置——凡是模拟器能跑出来的（空/密集数据、德语长文本、Reduce Motion、低电量、杀进程重进、错误态）必须当轮做完，只有真正依赖真机硬件/真实云/真实推送/真实数据规模的才允许进债；登记每条债时必须写明"为什么模拟器做不了"，写不出理由的不准后置。② 验收债必须在该模块 🏁 对抗复审前清零（复审以人工验收过的状态为基准）；③ Phase 9B feature freeze 前全部验收债必须清零；④ 验收债项与 9A 真机矩阵/dogfooding 合并执行（装机后集中过）。⑤ **滚动上限（防末期集中爆发）**：track list 里未清的 🟢\* 验收债**累计超过 15 项**时，下一个动作必须是插入一次**装机验收轮**把债排空，而不是再开新模块——验收债不设上限地攒到 Phase 9，正是 dogfooding 段落（Phase 9A）警告的"体验问题在最后集中爆发"。总览会话每次对账时核对计数，超限即在 `docs/testing-progress.md` 写一行最新状态并安排装机轮。

### 总览会话（Orchestrator）

总览会话**不改任何业务代码**，只做调度、对账、抽查。需要时才开（建议每完成 2~3 个模块开一次，Phase 8/9 必须由它主持）。Boot prompt：

> 读 `docs/ai-module-test-playbook.md` 和 `docs/testing-progress.md`，用 `git log --oneline -20` 与总账对账。你是总览会话，不修改业务代码。请：
> 1. 报告当前阶段进度、与总账不一致的地方（有 commit 没登记、有登记没 commit）。
> 2. 抽查最近完成的模块：重跑 `scripts/module-exit-gate.sh` 验证门禁仍然绿；抽看该模块门禁 commit 的 diff 是否与其交接备注/清单对应。
> 3. 检查 `docs/task-follow-ups.md` 余留项有没有升级为阻塞的。
> 4. 给出下一个模块的开工 boot prompt，并在 `docs/testing-progress.md` 的最新验证/交接区域追加一行必要状态。

### 并行会话规则

默认串行。确需并行时遵守 `AGENTS.md`：每个并行模块用独立 worktree（`git worktree add ../Ohana-<模块> -b codex/<模块>`），两个会话绝不共用一个 worktree；并行模块必须无共享文件交集（例如 Phase 7 的两个互不相关的小模块），地基层（Phase 1~4）一律串行。

### 提问协议（必停点，适用于任何 AI 工具）

模块会话在以下节点**必须停止输出、等待产品主人回答，禁止自答、禁止假设后继续**：

0. **动代码前置确认**——任何模块建设或修复在动代码前，必须先只读盘点：把检查后不懂的、不确定的、存在两种以上合理产品解释的内容全部列为问题交给产品主人确认；确认后先生成/更新并总结 `docs/specs/<模块>-logic.md`，再开始实现。
1. **1b 规则书完成后**——可疑清单必须以问题形式呈现（"代码现在是 X，意图是 Y 吗？"），每题给出 2~4 个选项和推荐项。
2. **第 2 步修复方案报告后**——影响面说完即停，等确认再动代码。
3. **发现宪法/规则书冲突或新的产品级二义性时**——立即停，不许按自己的理解先修。
4. **申请豁免注释时**——逐条列出，等批准。

**异步兜底**：若产品主人不在场，把阻塞性产品问题写成 `docs/task-follow-ups.md` 的开放项（编号、选项、推荐、关闭条件），暂停本模块、转做不被阻塞的工作。问题答复后销项。"我先按推荐做了"不是合法行为——推荐是给人选的，不是给 AI 自己选的。

**Codex 适配（plan 模式即必停点的强制载体）**：

- 第 1~2 步（1a/1b 分析 + 圈范围方案）用 **plan 模式**跑：规则书草稿与方案在 plan 中呈现，批准 plan = 完成必停点 1+2；未批准则代码零改动。
- Boot prompt 必须加一句：「规则书的可疑清单必须作为 plan 问题逐条向我提出（每题给选项+推荐），不许在 plan 里自行裁定产品意图」——否则 plan 模式只问技术问题、自答产品问题。
- Boot prompt 还必须加一句：「动代码前，把检查后不懂/不确定/有多种合理解释的内容全部问我；我确认后，先生成并总结 `<模块>-logic.md`，再开始实现」。
- 批准后的第一个执行动作 = 将确认过的规则书写入 `docs/specs/<模块>-logic.md`，再开始修复。
- **一个 plan 管一轮（3~5 条），不是一个模块**；下一轮重新进 plan 模式。
- 第 3~5 步退出 plan 自动执行（门禁兜底）；必停点 3/4（执行中的宪法冲突、豁免申请）plan 模式管不到，仍按上方协议停止或写入待拍板区。

### 收口与防返工规则

1. **地基冻结**：Phase 1~4 完成后，Models/Domain/Shared/App 的公共契约冻结。模块会话不得顺手改地基；需要改时记 follow-up，由总览会话凑批开"地基变更轮"（完整六步 + `--full` 门禁）。schema 升版流程是这扇门的样板。
2. **复审排序**：受未完成建设项（GAP-x）影响的模块，其 🏁 对抗复审排在该建设项落地**之后**（例：依赖照护派生执行器的 Economy 复审排在执行器结构收口之后），保证复审只做一遍。
3. **已知差距不重复发现**：模块会话遇到已登记的宪法差距（GAP-4~9）直接按归属领走，不当场修地基、不重新立项。
4. **根因重构轮**：当一个模块的待修清单（尤其对抗复审产出）中 ≥3 条共享同一根因时，不许逐条打补丁——开一个专门的根因重构轮：一个根因、一组表征测试、一次结构修正、行为修复跟进。复审反复在同一模块捞出同类问题 = 上一轮选了治标，技术债开始计息的信号。
   - **强制触发（打地鼠刹车）**：**同一根因在连续 ≥2 轮复审中复现**（哪怕每轮位置不同、看似"新"），立即停止点对点修复，强制开根因重构轮。典型信号：一个横切不变量沿调用栈层层暴露（owner→事实→命令→UI 每轮往外推一层）。
   - **结构修正的验收标准是"让该类 bug 无法表达"**，不是"又堵了一层"。负向不变量（要求某些副作用不发生）必须靠**类型化信号 + 强制消费**封死（如收口返回 `disposition{didWriteFact, allowsDerivedEffects}`，调用方必须消费，配审计禁止用启发式猜状态），而不是靠每个调用方记得检查。判据：下一轮复审应"构造不出绕过"，而非"又找到第 N 个绕过点"。

### 复审熔断（硬规则，防止第 N 轮循环）

复审-修复循环对**横切不变量**在数学上不收敛：违反点 = 调用栈所有分支 × 所有派生点，是组合爆炸空间，复审只能采样，永远采不完。复审的职责是**分类**（这是离散 bug，还是一个横切根因的多个表现？），不是穷举——别指望"一次查全所有问题"，那理论上不可达（采样无穷空间 + 发现会改变可发现性 + 根因分层）。能达成的是"一次根治"，但路径是**早识别横切根因 → 早转架构封死**，不是更彻底的复审。

**单轮内根因聚类（强制，2026-06-14）**：纯复审会话输出 P0/P1/P2 清单**之前**，必须先输出一段「根因聚类」——把本轮发现按根因归组。**任一根因在单轮内有 ≥3 个表现，当轮立即触发熔断**，直接进架构封死，**不进逐条修复**。不要等跑满 3 轮、6 轮才反应过来。这把"识别横切根因"从事后回顾提前到复审当场。

**跨轮强制归因（硬规则，2026-06-15 教训）**：熔断最大的失效点是——表面不同的发现（不同 feature/字段/措辞）藏着同一个根因，而无记忆的纯复审会话只看本轮、看不到这是第 N 次同类。所以归因责任不能悬空。**纯复审会话在输出发现之前，必须先读总账里本模块的全部历史复审记录**，对本轮每个发现标注：「新根因」或「历史 TFU-XXXX 同根因复现」。**任一历史根因第 3 次复现（跨轮累计，不要求同轮）→ 当轮熔断转架构。** 关键认知：判定熔断要把表面不同的发现**抽象到根因层**再数（例：milestone orphan ledger + deceased executor actor 不一致 + memorial 写入门，表面是三个 bug，根因都是"成员状态变化后的引用完整性/写入门"——按根因数算就是同一个 ≥3）。这条同时治"对账日志没人读全"：它强制复审会话读历史。

当出现下列任一信号，**立即熔断**：

1. **单轮内同一根因 ≥3 个表现**，或同一根因**连续 ≥2 轮**复现；或
2. 某轮发现的本质是"同一句话换一个入口/派生点"（如"某处 no-op/历史/冻结时仍发了某副作用"反复出现）；或
3. 已经给收口加了类型化信号（disposition 等），但违反仍在出——说明**信号是建议、权力没收走**。

熔断后**禁止再开复审-修复轮**，强制转**架构改造**：把产生违反的那个能力从分散的调用方**收回到单一执行器**，让违反在编译期/审计期无法表达（典型：副作用触发权从各 command 收回 `*DerivationExecutor`，command 失去直接发副作用的 API）。

熔断的判定信号：**"加了字段/规则但还在漏" = 权力没收走**。解药不是再加一条规则，是收走能力。架构改造的验收是"构造不出绕过"，**且全程只在结尾做一次复审**（架构对则必零发现）——不再用复审驱动修复。

> 反面教训（2026-06-14，Economy/care-completion）：同一不变量（no-op/历史/冻结时副作用未抑制）连续 14 轮复审未收敛，因为每轮都选了点对点补丁、且 disposition 字段只是建议（权力仍在各 command）。熔断规则即为防止此类循环重演。架构方案见 `docs/planning/care-derivation-executor-spec.md`。
5. **质量复查**：治本轮收工前，对改动文件做一次简化/复用复查（删除重构后的死代码、合并重复逻辑、确认抽象没有过度设计），作为门禁前的最后一步。
6. **方案推荐默认治本**：当 plan 问题或修复方案在“局部小改 / 一次性彻底解决”之间选择时，默认推荐彻底解决。尤其是 P0/P1、共享根因、服务层硬门、数据一致性、奖励/资产、权限/隐私、删除恢复、通知派生状态、CloudSync/备份地基、未来会被多模块复用的逻辑，推荐项必须优先让代码结构直接表达规则书语义并补测试护栏。只有纯 UI/文案低风险项、已被硬门保护的不可达未来功能、或彻底方案会跨模块/schema/启动路径且超出当前批准范围时，才可推荐治标；推荐治标必须同步写明技术债去向、TFU 条目或关闭条件。

| 谁 | 负责什么 |
|---|---|
| 模块会话 AI | 静态分析、跑审计、写/跑测试、修复、生成人工验收清单、跑退出门禁 |
| 总览会话 AI | 调度、对账、抽查复验、主持 Phase 8/9 |

## 三、工具箱与模块退出门禁

| 命令 | 用途 |
|---|---|
| `scripts/module-exit-gate.sh` | **模块退出门禁**：changed 审计 + 本地化 parity + 全量单测，一条命令 |
| `scripts/module-exit-gate.sh --full` | **阶段边界门禁**：全仓 `--all` 审计 + 架构边界 + 全量单测 |
| `scripts/dev-check-changed.sh` | 改动文件的廉价首检 |
| `scripts/build-debug-fast.sh` | 快速 Debug 构建（iPhone 17 模拟器） |
| `scripts/test-simulator.sh -only-testing:OhanaTests/XxxTests` | 修复迭代中的定向测试 |
| `scripts/audit-*.sh` | 各专项审计（ui-v4 / accessibility / smoothness / runtime / localization / architecture） |
| `scripts/release-hardening-check.sh` | 上架前总检 |

门禁使用时机：
- **每个模块收工前**：`scripts/module-exit-gate.sh`（含全量单测——这保证"每个模块完成后，app 自己跑一遍测试"）。
- **每个 Phase 结束、进入下一 Phase 前**：`scripts/module-exit-gate.sh --full`，由总览会话执行。
- 修复迭代过程中用定向测试加速，门禁只在收工时跑（全量测试贵，不当心跳用）。

然后**你逐条确认**这份规则书：意图对的打钩；与产品意图不符的就是 bug，并入 P0/P1 清单。确认过的规则书就是该模块的逻辑基准——复审、回归、未来加功能都对着它检查。

### 第 3 步：修复（先红后绿；治本走护栏三件套）

**Prompt 模板（B 治标路线）：**

> 按确认的方案修复。每个行为型 bug：先写能复现它的 Swift Testing 测试（in-memory SwiftData），确认是红的，再修到绿。
> 外科手术式改动：不重构无关代码、不改无关格式。每修完一条用 `git diff --stat` 报改动面。

**Prompt 模板（A 治本路线，护栏三件套）：**

> 按确认的治本方案重构。护栏三件套，缺一不可：
> 1. **表征测试先行**：动手前为受影响的现有行为补"锁行为"测试（以规则书为准描述外部可观察行为），全绿后才开始改——这是重构的安全网，也是"重构没改坏东西"的证明。
> 2. **重构 commit 与行为 commit 分离**：纯重构提交（行为不变，全部测试不动且全绿）与行为修复提交（带先红后绿的新测试）严格分开，禁止混在一个 commit。Review 时重构 commit 看"测试零改动+全绿"，行为 commit 看"红变绿"。
> 3. **大改走两步走（expand–contract）**：先并行落地新路径并切换调用方（旧路径保留可回退），门禁全绿后下一个 commit 再删旧路径。每一步独立可回滚。
> 每个 commit 用 `git diff --stat` 报改动面。

> **表征测试不可篡改（铁律，2026-06-14 教训）**：表征测试一旦写定，它的输入和断言就是行为金标准。重构后表征测试**变红，只有两种合法反应**：① 举证证明是"测试写错了但行为等价"（罕见，需说明为何外部可观察行为没变）；② **承认行为被改了，停下来判断这个改变对不对**（可能是 bug，可能需产品决策）。**绝对禁止：为了让红测变绿而修改表征测试的输入或断言。** 把测试输入改成能通过的值（如把无效 `executorId: "human-1"` 改成真实 UUID），等于把"行为被改"的证人灭口——你从此再也看不见回归。Review 时：**表征测试文件的任何改动都要单独审，问"这是不是在洗白一个行为变更"**。

> **测试断言必须符合宪法（铁律，2026-06-14 教训）**：测试变绿不等于行为正确。一个**断言了违反宪法行为**的测试，本身就是 bug——它给一个违规行为盖了"通过"的章。典型：宪法 ECO-026④ 要求"脏/已删 executor 仍写 active 对象事实"，但测试写 `executorId:"human-1"` → `PetCareLog isEmpty` 并通过，等于用绿测试假装"丢事实"是对的。**检阅/复审时必须对照三方，不止两方**：代码 vs 宪法、**测试断言 vs 宪法**、代码 vs 测试。三者任一不一致即为缺陷；尤其当代码、测试、对账自述三处都"自洽地错"时（都按错误行为写），更要回到宪法这个唯一外部锚点裁决。新写测试时：断言先问"这个期望符合宪法/规则书吗"，再写。

**外科手术的边界澄清**："外科手术式"约束的是**不碰无关代码**，不是**不许动结构**。根因在本模块内且方案 A 已被批准时，果断重构是协议要求而非违规（AGENTS.md 的反欠修复条款）；用补丁掩盖结构问题、让同根因症状在复审里反复出现，才是违规。

**验收标准：** P0/P1 各有"先红后绿"测试（纯视觉瑕疵除外）；治本路线额外要求表征测试在重构 commit 前全绿；diff 每一行能对应清单某一条或已批准的重构方案。Review 时**先看测试 diff 再看实现 diff**。

### 第 4 步：补测试覆盖

#### 覆盖率地板（客观护栏，给主观复审兜底）

对抗复审是主观的——它度量"敌意视角挖不出新根因"，但回答不了"测试是不是真的测到了代码"。"不刷凑数测试"目前只是一句口号，没有机制检测。所以核心地基层加一条**客观行覆盖地板**作为交叉验证：

- **范围与阈值**：`Ohana/Domain` 与 `Ohana/Features/Economy` 行覆盖 **≥ 70%**。这两处是钱/资产/不变量的所在，主观复审最不该独力承担的地方。其余模块暂不设硬地板（避免为覆盖率而测的反模式），但鼓励参考。
- **口径**：覆盖率是**地板不是目标**——70% 用来抓"整片未测的服务/分支"，不是逼到 90%+ 去测 getter。低于地板必须解释（要么补测试，要么标注"这段是不可达的未来功能/纯样板"并豁免）。覆盖率高也**不**等于成熟：它和对抗复审是正交的两个信号，都要过。
- **执行**：需要 `scripts/audit-coverage-floor.sh`（`xcodebuild test -enableCodeCoverage YES` + `xcrun xccov view --report --json` 抽取按路径覆盖、与阈值比对，低于即非零退出）。脚本落地前，本条在 🏁 复审时**人工核对一次**（`xccov` 报告附进交接备注）；脚本落地后并入 `scripts/module-exit-gate.sh`。这条规则在脚本化之前同样适用"prose 规则形同虚设"的警告，应尽快补脚本 + fixture。

## 发布门槛（Release Bar）—— 首发的唯一停止条件（2026-06-15 立，最高优先级）

**核心认知**：扫不出 bug 永不发生——bug 空间是组合爆炸的无穷集，对抗复审的设计目标就是不断发现，给它无限时间它无限发现。所以"复审零发现 / 🏁"是个**永不到达的终点**。把它当首发门槛，等于把自己锁进复审-修复怪圈。成熟团队从不追"零 bug"，追的是**分流**："这个 bug 严重到必须挡首发吗？"——绝大多数答案是"不，上线后修"。

**首发门槛矩阵**（严重度 × 首发可达性）：

|  | 首发可达（单机/单用户/核心流程会触发） | 首发不可达（CloudSync `.none`/联机/功能门后/极端边角 0.01% 路径） |
|---|---|---|
| **P0**（崩溃 / 数据丢失 / 隐私泄漏 / 核心流程完全断 / 钱·椰子算错） | **🔴 唯一挡首发的格子** | 🟡 登记 backlog，1.x 修 |
| **P1**（有缺陷但有 workaround） | 🟡 登记 backlog，上线后修 | 🟡 登记，1.x 修 |
| **P2**（瑕疵 / 边角 / 不一致） | 🟢 带走，上线后修 | 🟢 带走 |

**首发门槛 = "P0 且首发可达"清零。** 这一格有限（核心流程上的崩溃/数据丢失/经济算错，数量可数，几天可扫清）。其余全部登记进 `docs/task-follow-ups.md`（上线后修复 backlog），带着上线，按版本排期。

**操作上只改复审问的问题**：从"还有没有问题？"（无限）→ "**还有没有 P0 且首发可达的？**"（可数，清零即发）。复审仍做，但任务从"找所有 bug"变成"确认那一格为空"。

**🏁 的定位修正**：🏁（对抗复审零发现）是**上线后持续追求的长期成熟度目标，不是首发阻塞**。原"核心五模块必须 🏁 才能进 Phase 8 / 才能发"的门槛**作废**——它把无限过程当终点，是怪圈的制度根源。Phase 8 / 首发的准入改为**全局"P0+可达"清零**。🏁 留作上线后每个模块逐步逼近的质量标尺。

**审计继续跑**：member-gate / economy / derived-state 等审计的价值是**防新 bug（债不反弹）**，不是清空旧 bug。上线后持续优化时，它们保证你修旧债的同时不进新债。

### 模块成熟度准则：对抗性复审（🟢 → 🏁，上线后长期目标）

🟢 只代表"本轮发现的问题修完且门禁绿"，**不代表成熟**。历史经验：每个全新会话都能在同一模块查出新问题——把这个现象变成流程武器：

- 模块 🟢 之后，**开一个全新会话**（零历史上下文）做对抗性复审。复审会话不读修复会话的清单，只读规则书和代码，避免视角被污染。
- **复审 Prompt 模板：**

  > 读 `AGENTS.md`、`docs/ai-module-test-playbook.md`、`docs/specs/product-foundation.md`、`docs/specs/<模块>-logic.md`。你是对抗性审查者，目标是**推翻**这个模块：对照产品宪法的 D 条款与 G1~G8 不变量，在 `Ohana/Features/<模块名>` 里找出业务逻辑错误、规则书与代码的不一致、并发/时序漏洞、多成员多宠物边界错误、数据迁移隐患。假设之前的会话有遗漏，专挑没人测过的路径。输出 P0/P1/P2 清单，每条带 `文件:行号` 和复现思路。**只分析不修改。**
  > 复审时必须重新跑 1b 的九类全域问题雷达：可用性、必要性、业务/数值合理性、身份归属、状态机/时间/并发、副作用顺序、持久化演进、验证护栏都要逐项攻击；不能只复查上一轮修过的点。

- **成熟判定（带停止条件，防无限复审）**：一轮全新会话复审若**没有查出新的 P0/P1 根因**，模块即标 🏁。这里"新"是关键——已在规则书/测试护栏里记过的根因被复述、或只是同一已知问题的换皮表述，**不计为新发现**；判据是"有没有冒出此前没被规则书或测试覆盖的实质缺陷根因"，不是"复审会话有没有提出任何意见"。一个有创造力的审查者总能挑出措辞或边角 nitpick，所以门槛设在**新的实质根因**，而非"零意见"。查出**新的** P0/P1 根因 → 回六步循环修复（修复进规则书+测试），修完换新会话再复审。每轮的新发现都被护栏吸收，所以新根因数单调收敛，通常 1~2 轮归零。等价表述：**当复审只剩 P2 / 只剩已登记项时即判 🏁**。
- **采样节奏**：不要把全部模块修完才开始复审。每完成 3~4 个工作项，插入一次对核心件的对抗复审采样——如果采样干净，说明当前节奏的质量是真的；如果采样捞出 P0，立即放慢、先修标定再继续。高速批量产出（如一天多个模块）之后，复审采样是强制的下一步。
- **衔接规则**：在"业务逻辑重建（1b）"加入流程之前已 🟢 的模块没有规则书。其复审会话先执行 1b（从代码反推规则书、经你确认），再做对抗审查——一次会话完成补课和复审。

### 🏁 完整性防呆（防止自我打分）

🏁 被多次过早套用（实现者用"机器门禁绿 + 我重跑了一遍"冒充对抗复审）。三条硬规则：

1. **🏁 只能由"纯复审会话"授予**——该会话本轮不得改任何业务代码（只读分析 + 写发现）。修复会话跑完门禁后最多标 🟢，**不得自标 🏁**。
2. **🏁 必须在总账引用复审会话的独立证据**：复审会话身份/轮次 + 该轮发现数（哪怕为 0 也要写"某会话复审，0 P0/P1"），不能只写"重审零 P0/P1"这种无主语断言。
3. **🏁 自动失效**：任何改动该模块业务代码的后续 commit（含跨模块重构波及它），自动把它降回 🟢，必须重新走一次纯复审会话才能恢复 🏁。重构改了复审基线，旧 🏁 不再有效。

总览会话对账时，对每个 🏁 核验上述三条；不满足即降级。
- P2 不阻塞 🏁，记入 task-follow-ups。
- **🏁 可被重新打开**：已 🏁 的模块若日后（其他模块复审、集成、dogfooding）暴露出新的 P0/P1 根因，状态降回 🟢，修复后须再过**一轮干净复审**才能重新 🏁——🏁 是"截至最后一轮无新根因"的快照，不是永久证书（Economy 的 🏁→🟢 就是这条规则的实例，属正常，不算流程失败）。
- 复审结论（轮次、最后一轮**新根因**发现数，应为 0）记入总账交接备注。

这是对"能不能保证成熟"最诚实的回答：无法证明没有 bug，但可以**测量收敛**——当带着敌意的全新视角也挖不出**新的实质根因**时，模块才算成熟。核心模块（Domain、Economy、Feeding、Members、Home）优先追求 🏁，但 Phase 8 / 首发门槛以全局 **P0 + first-release-reachable 清零**为准；未达 🏁 的成熟度工作进入上线后持续质量目标。

3. **Dogfooding**：主理人用真实数据每日使用，从现在起持续到上架（≥2 周）；发现即记总账。两条护栏：只安装**过了门禁的 main 提交**（每个 🟢 模块落地后更新一次），不装会话中途的工作树；GAP-3 自动备份落地前每周手动导出一次存档。Dogfooding 不是成熟后的验收，而是与对抗复审平级的发现渠道——它找的是"用起来烦不烦"这类测试找不到的问题，等成熟再用会让体验问题在最后集中爆发。
   - **真机签名先配**（前置依赖）：付费账号已就位，Xcode 配好 Team + 用 "Ohana Local Device" scheme 装机。这是 dogfooding 与全部 91+ 验收债的共同前置，**不配则验收债全部撞墙在 9B**。
   - **验收债绑定 dogfooding 燃尽**：`gap-acceptance-track-list.md` 的真机/真实 UI 项不攒到 9B，每天用 app 时顺手勾。总览会话每次对账报告"验收债燃尽进度"（已勾/总数），防止它再无声膨胀。
4. **可用性观察**：3~5 名真实宠物主人现场走 D17 的 90 秒闭环，观察卡点（app 无埋点，上线后没有漏斗数据，这是唯一的转化验证窗口）。
5. **本地化质感**：zh/en 人工全量过；其余七语言抽查核心流或首发商店页仅列 zh/en（顺势关闭 O4）。
6. **无障碍真验收**：VoiceOver + 最大动态字号在真机过核心五流程（建岛、记录、任务、经济、纪念）。

#### 9B RC 纪律（Phase 8 全绿后）

1. **Feature freeze**：宣布冻结后只接收 blocker 修复，一切其他改动进 1.x。
2. **RC 构建**：Release 配置 archive 即 RC；**构建不可变——测过的构建就是提审的构建**，任何代码改动 = 新 RC 重测。
3. **RC 全量回归**：Phase 8 端到端清单在真机 + RC 构建上重跑；**备份→擦除→恢复演练用 RC 做**（含一份长期使用产生的"老备份"恢复）。
4. `scripts/release-hardening-check.sh` 全绿 + `PrivacyInfo.xcprivacy` 与 required-reason API 实际使用比对 + `scripts/audit-localization-coverage.sh` 零缺口 + 按 `docs/release-quality-gates.md` 出最终发布报告。
5. TestFlight 分发 RC，内测 1~2 周，盯 MetricKit 崩溃/卡顿。

#### 9C 提审与上线后

1. **提审材料**：各尺寸截图（真实数据，不造假）、隐私问卷（必须与 PrivacyInfo 一致——高频被拒原因）、年龄分级、**出口合规加密声明**（仅标准加密→豁免）、审核备注（无需账号即可全功能体验；定位仅用于遛狗记录）。
2. **预期管理**：首次提审 24-48h+，新账号新 app 被拒率偏高；被拒把拒绝信原文交给 AI 分析整改，不慌。
3. **开启分阶段发布（phased release）**——App Store 无法回滚，分阶段发布是仅有的两道保险之一（另一道是热修）。
4. **上线后 7 天运维节奏**：每日看 App Store Connect 崩溃 + MetricKit 摘要；预设 1.0.1 触发阈值（崩溃率异常/任何数据丢失类反馈即 blocker）；知道加急审核（expedited review）申请路径；保持一个随时可发 1.0.1 的干净分支。

## 六、全程反模式清单（每个会话适用）

1. **一个会话一个模块。** 模块会话不许越界修别的模块；发现跨模块问题写交接备注，由总览会话调度。
2. **不接受没有输出的"已验证"。** 任何验证主张要命令 + 输出摘要。
3. **测试 diff 先于实现 diff 看。** 防止为绿而绿。
4. **豁免注释一律人工审批。** `// xxx: allow` 是审计后门。
5. **schema、启动、隐私、删除路径单独成轮单独 commit。**
6. **收工必更新 `docs/testing-progress.md`。** 没更新总账 = 没完成；总览会话对账时以 git history 为准纠偏。
7. **门禁不绿不提交；完成的工作项或 coherent fix batch 即推（`main` 领先 `origin` ≤ 1 工作项）；CI 因已登记外部 blocker 红时停下、不刷同一红点。** "不刷 CI"只约束**重复触发已知红点**，不约束推送完成的工作；同时不要把同一 coherent repair 拆成多个 push 只为采样 CI。攒多个工作项不推才是真正的反模式（见收工协议第 5 条）。不绕过、不 force push；外部 blocker 红点记录 run 和 TFU 后停止触发新 run，直到进入该 blocker 的修复轮。
8. **并行必用独立 worktree。** 两个会话共用一个 worktree 是事故之源。
