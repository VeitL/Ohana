## 基本信息

App 名称：Ohana

一句话定位：认真记录照护的家庭，值得一座越来越繁茂的岛。

当前阶段：MVP / Release Candidate 准备期。当前处于 Phase 9A（dogfooding 与真机验证），
尚无仓库证据表明已经公开上线或完成 TestFlight 发布；当前发布门槛为 Open P0 = 0、
首发可达仓库代码 P1 = 0。

目标用户：家庭中承担主要照护责任、希望用一台 iPhone 统一记录家庭生命照护的主理人。
首发以养宠家庭为核心，犬猫是第一公民动物物种；植物在 Lv.4「家庭树冠」进入同一照护闭环，
人类成员在首发主要作为被照护档案，而非独立在线操作者。

用户最重要的 Job-to-be-Done：当我独自承担家庭照护时，我需要在几秒内知道今天该做什么、
记录已经完成的喂食/饮水/遛狗/清洁/用药等照护，并可靠地保留提醒、健康历史和家庭记忆，
这样我不会遗漏照护，也能长期看见这个家的成长。

目标市场和 App Store 地区：面向消费级、宠物优先并延伸到植物与家庭生命管理的 iOS 市场。
具体首发国家/地区尚未在产品基石中拍板；当前倾向是中文与英文商店元数据先行，不能据此假定
已决定中国、美国、德国或全球同步首发。Phase 9 提审前必须确认首发地区、定价币种、隐私与
商店元数据范围。

支持语言：App 内当前注册 9 种语言——简体中文、英语、德语、西班牙语、葡萄牙语（巴西）、
法语、日语、韩语、意大利语。中文和英文是作者阶段的必备语言，也是当前商店元数据优先方向；
其余语言可走英文/中文回退链，但发布前仍需核对商店元数据和长文本视觉质量。

最低支持 iOS 版本：当前所有 target 的 `IPHONEOS_DEPLOYMENT_TARGET` 为 iOS 26.2。
这是真实项目配置，但 `docs/os-support-matrix.md` 已将其标为“action required”且很可能过窄；
产品负责人尚未确认最终最低版本。任何下调都属于需要 API 可用性审计、fallback、最低版本
模拟器构建与回归测试的迁移，不能只改一个 build setting。

技术栈：

- UI：SwiftUI；图表使用 Swift Charts。
- 数据：SwiftData，本地 schema 当前为 `ArkSchemaV85`；首发以本地持久化为准。
- 云与备份：首发提供手动导出和 iCloud Drive 文件备份/恢复；CloudKit 同步与 CKShare 代码作为
  1.x 地基保留，但当前 SwiftData 配置明确使用 `cloudKitDatabase: .none`，首发不启用多人云同步。
- Apple 平台能力：Core Location / MapKit（仅运行中的遛狗允许后台定位）、HealthKit、
  UserNotifications、MetricKit。
- 工程：Swift 5 language mode、Swift Testing 单元测试、XCTest UI tests；Xcode 项目当前无第三方
  Swift Package 产品依赖，也未接入 Firebase、Supabase 或自建后端。

商业模式：信任型 Freemium。

- Ohana Solo：永久免费，提供单设备、单主理人的完整本地照护闭环，不按宠物/植物数量、记录条数
  或历史长度收费。
- Ohana Family：规划为订阅 + 终身买断，售卖多设备同步、多主人协作、共享提醒、权限和家庭资产
  保护；首发不可达，最终商品名与价格点仍待 Phase 9 提审前确认。
- Ohana Care+：未来高级层，面向 AI 总结、智能洞察、植物识别/病害分析、天气联动等；不属于首发。
- 数据红线：取消订阅、试用结束或购买失败不得锁住、删除或隐藏用户已有的本地数据、基础提醒、
  导出和纪念模式；不卖椰子，不以离世宠物制造付费转化。

## 核心用户流程

1. 首次价值闭环：建岛 → 创建第一只宠物 → 完成第一笔照护记录 → 获得第一把椰子 →
   看到绿洲种子发芽；目标是在 90 秒内完成，加入他人岛屿的路径首发隐藏。
2. 日常照护闭环：首页 / Today Focus 提示今日重点 → 用户通过 Quick Care 或详情页记录照护 →
   领域命令写入一个业务事实 → 同步提醒、任务、奖励、账本与 read-model revision → 首页给出轻量反馈。
3. 长期家庭生命周期：持续积累健康、花费、照片、里程碑和周报 → 通过手动导出与 iCloud Drive
   文件备份保护数据 → 成员离世后退出活跃照护并进入只读照护、可写回忆的纪念模式；确认永久删除
   则物理删除成员及从属记录。植物于 Lv.4 解锁后复用本地档案、任务、提醒、日志和历史闭环。

## 关键业务规则

1. 业务事实与派生必须分层：View 不得直接改椰子余额、提醒、家庭任务、奖励或账本副作用；
   快速照护只能进入一个领域服务/命令执行器、写一个业务事实，再由统一服务派生奖励、提醒、任务、
   ledger 和 read-model 更新。椰子奖励只能通过 `QuestManager` 及审计过的经济入口发放。
2. 生命周期必须一致：active 成员可以写照护事实；离世成员的照护新增、编辑、补记和经济派生必须
   no-op，但照片、回忆、纪念日和悼念笔记可继续新增且不得触发奖励/连胜/任务。永久删除必须明确
   二次确认并物理真删，用户不可见回收站；未来云同步只可保留不可恢复的同步 tombstone。
3. 首发必须本地自洽且信任优先：一个主理人 + 一个生命就是完整家庭；首发不得出现邀请、认领、
   指派或任何依赖另一名在线用户的流程。基础宠物与 Lv.4 植物照护永久免费，植物门与联网门不得
   耦合；备份失败必须可见，恢复旧备份必须提示可能重新带回后来删除的数据。

## 已知直接竞品

以下是本次审计的起始竞品集，不代表已经完成市场份额或地区可用性研究：

1. [11pets](https://www.11pets.com/en/feature)：综合宠物照护、医疗记录、卫生、营养、日程与提醒，
   可对照 Ohana 的宠物档案深度、提醒和数据导出。
2. [DogLog](https://apps.apple.com/us/app/doglog-track-your-dogs-life/id1229529595)：记录喂食、饮水、
   遛狗、排泄、用药等日常活动，并覆盖家庭/照护者协作、提醒、统计与兽医导出，直接对照 Ohana
   的 Quick Care 与未来 Family 协作。
3. [PetDesk](https://petdesk.com/download-app-for-pet-health/)：以宠物健康、就诊、疫苗/用药提醒、
   医疗记录和服务商连接为核心，可对照 Ohana 的健康档案、Documents/Insurance 和提醒可信度。

## 值得参考的非直接竞品

1. [Planta](https://getplanta.com/?language=en)：植物个性化照护计划、智能提醒、识别、病害建议和
   Care Share，可对照 Ohana Lv.4 基础植物体验与未来 Care+ 边界。
2. [Cozi Family Organizer](https://www.cozi.com/)：共享家庭日历、成员视角、清单、待办与通知，
   可对照未来 Ohana Family 的协作信息架构，但不应把多人协作提前泄漏进 Solo 首发。
3. [Finch](https://help.finchcare.com/hc/en-us/categories/37934152903309-Finch-Features)：以目标、连胜、
   quest、奖励、收集和空间装扮强化习惯，可对照 Ohana 的椰子、Oasis、商店与游戏化克制度。

## 我最担心的地方

1. 产品范围稀释核心承诺：宠物、植物、人类轻照护、提醒、健康、花费、相册、纪念、经济、商店、
   周报和未来协作同时存在，容易让“90 秒完成第一次照护价值”和“三秒记一笔”被次级模块拖慢。
2. 跨模块派生的一致性与数据安全：一次照护会触发任务、提醒、奖励、账本、首页刷新、备份和
   生命周期过滤；任何旁路写入、重复派生、删除残留或旧备份恢复语义错误都会直接伤害用户信任。
3. 发布证据与市场决策仍有缺口：最低 iOS 版本、首发 App Store 地区、最终价格/商品命名尚未拍板，
   真机通知、HealthKit、后台定位、iCloud Drive 失败恢复和真实硬件性能也不能由模拟器结果替代。

## 已知问题

1. 最低系统版本目前锁在 iOS 26.2，现行 OS 支持文档明确认为可安装用户面可能过窄；最终支持范围
   和兼容迁移尚未决策。
2. Phase 9A 真机验收未完成：当前仍需在真实 iPhone 上完成 Solo Release R1–R6、通知真实投递与
   action、纪念成员通知取消/恢复、HealthKit 授权/样本读取、锁屏后台遛狗以及 iCloud Drive
   失败/重试等验证。2026-07-10 最近一次记录中，物理 iPhone 离线/不可用。
3. 当前共有 7 个开放 follow-up：5 个 P1 均为 CloudKit 1.x 或真机外部验证，2 个 P2 分别是更深的
   Pet simulator GUI 覆盖和 Members/Pet/Plant 长语言视觉扫尾。当前没有已知首发可达仓库代码 P1，
   但 CloudKit live apply 在启用前仍需真共享区验证，P2 债务也不应被误写成已经完成。

## 审计目标

1. 为 App Store 1.0 / Release Candidate 做发布前审计，确认首发可达面没有 P0/P1 代码缺陷，
   feature gate 不泄漏未来联网能力，且真机与商店前置项有明确关闭证据。
2. 检查 AI 辅助生成和长期演进后的代码质量：领域边界、SwiftData actor/Sendable 边界、路由首帧、
   高流量查询、缓存归属、后台工作、动画循环、可维护性和测试有效性。
3. 对抗性检查关键业务逻辑：照护事实唯一写入、奖励防刷与钱包恒等、提醒/任务同步、离世成员退场、
   物理删除、备份/恢复、隐私、失败写入与重复提交。
4. 检查产品基石、模块规则书、工程规则、UI token、状态台账与当前源码是否一致，并区分当前政策、
   已实现代码、feature-gated 未来代码和历史规划，防止用旧文档覆盖现状。
5. 与宠物照护、家庭协作、植物照护和游戏化习惯产品做结构化对比，判断 Ohana 的差异化是否真正
   落在“家庭生命组合 + 长期记忆 + 信任型 Freemium”，并识别首发功能过载或关键能力不足。

## 文档权威顺序

发生冲突时，以下文档与证据从高到低排序：

1. 当前用户明确指令。
2. `docs/specs/product-foundation.md`：产品行为与验收事实的最高权威。
3. `AGENTS.md`：工程工作流、仓库导航、架构边界和验证规则。
4. `ui规范.selection.json`：UI token 与组件选择的机器可读事实来源。
5. `docs/` 下现行治理文档与模块规则书；发布状态分别以 `docs/testing-progress.md`、
   `docs/task-follow-ups.md`、`docs/planning/gap-acceptance-track-list.md`、
   `docs/cloud-sync-todo.md` 的职责边界为准。
6. 当前源代码、项目配置和可复现测试/构建证据。
7. 历史 planning/reference/archive 文档；与以上来源冲突时视为过时证据，不得反向定义当前产品。

若现行高权威文档本身没有决策，例如首发 App Store 地区、最低 iOS 版本或最终价格点，审计必须
明确提出决策建议和验证成本，但不得自行把某一历史文档、代码默认值或推测当成最终产品事实。
